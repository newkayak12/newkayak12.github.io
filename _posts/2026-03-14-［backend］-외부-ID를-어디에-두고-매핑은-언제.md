## 1. 외부 시스템이 준 ID, 어디에 쓰일까?
- 외부 판매 채널에 우리 상품을 등록하는 연동을 설계했다. 상품을 보내면 채널이 **자기 쪽 상품 ID**를 발급해 돌려준다.
- 이 ID는 두 곳에서 쓰인다.
	- 상품을 수정하거나 상태(활성/비활성)를 바꿀 때: 채널에 "이 상품"을 가리키려면 이 ID가 필요하다.
	- 채널에서 주문(출고 요청)이 들어올 때: 주문에는 채널의 ID가 실려 온다. 이걸로 우리 상품을 찾아야 한다.
- 그래서 질문이 둘이다.
	1. 이 ID를 어디에 저장할까?
	2. 들어온 주문을 내부 상품에 잇는 매핑을 언제 만들까?
- 시스템에는 이미 쓰이던 구조가 두 가지 있었다.
	- **상품별 외부 연동 코드**: 상품 하나에 "연동처 + 그 연동처에서의 코드" 행을 여러 개 달 수 있는 범용 구조다. 연동처 목록은 공통 코드로 관리하고, 사용자가 화면에서 직접 등록·수정한다.
	- **주문 상품 매핑**: 주문에 적힌 상품명을 내부 상품으로 잇는 테이블이다. 주문 수집은 이 매핑을 보고 상품을 특정한다. 주문 하나에만 쓰는 "단건 매핑"도 이미 있다.

## 2. 행 추가? 마스터 컬럼? 전용 테이블?
- 저장 위치 후보는 셋이었다.

| | 1. 기존 연동 코드 구조에 행 추가 | 2. 상품 마스터의 기존 컬럼 | 3. 전용 테이블 |
|---|---|---|---|
| 저장 | 연동처 코드를 하나 새로 만들고 상품마다 행 하나 | 상품 행의 채널 상품 코드 컬럼에 바로 | 상품과 외부 ID를 잇는 테이블을 새로 |
| 좋은 점 | 이미 있는 구조와 로직을 그대로 씀 | 조회가 가장 편함 | 뜻이 분명하고 다른 데이터와 섞이지 않음 |
| 걸리는 것 | 사용자가 화면에서 고칠 수 있음 | 확장에 제한이 됨 | 관리 포인트가 늘어남 |

- 깔끔함만 보면 3이다. 그런데 테이블 하나가 늘면 그걸 쓰고 읽는 로직, 조인, 마이그레이션이 같이 는다. 이미 "상품 × 연동처" 모양의 구조가 있는데 같은 모양을 하나 더 만드는 셈이다.
- 그래서 깔끔함 대신 두 질문으로 따져 봤다.
	- 누가 그 값을 바꿀 수 있나?
	- 연동처가 늘 때 무엇이 막히나?

> 결과적으로 **1을 선택했다.** 처음 설계한 대로 기존 범용 구조를 쓰고, 걸리는 점은 플래그로 막았다.

## 3. 누가 그 값을 바꿀 수 있나?
- 외부 ID는 채널이 발급한 값이다. 우리 쪽에서 사람이 고칠 이유가 없다.
	- 누가 고치면 수정·상태 변경 요청이 엉뚱한 상품을 가리키거나 실패한다.
	- 주문이 들어와도 상품을 찾지 못한다.
- 그런데 1번 구조는 원래 **사용자가 화면에서 관리하던 구조**다. 그대로 행을 넣으면 이 값도 화면에 보이고 고칠 수 있다. 1번의 "걸리는 것"이 이것이다.
- 그래서 행에 노출 여부를 따로 두었다.
	- 이 연동처의 행은 화면에서 **노출, 등록, 수정, 삭제가 모두 안 된다.**
	- 연동처 공통 코드도 새로 추가하되 화면에는 노출하지 않는다.
	- 값은 상품을 등록할 때 채널 응답을 받아 시스템이 직접 넣는다.
- 저장 위치는 공유하고, 쓰기 주체만 나눈 것이다. 같은 테이블에 있어도 **누가 쓰는지가 다르면 다른 데이터**로 다뤄야 한다고 생각했다.

> 결과적으로 **저장 위치는 재사용하고, 쓰기 주체는 플래그로 나눴다.**

- 물론 대가가 있다. 이 구조를 읽는 화면 쪽 조회는 모두 이 플래그를 알아야 한다. 조건 하나가 빠지면 숨긴 값이 보인다.
	- 전용 테이블이었다면 화면이 애초에 그 테이블을 모르니 이 걱정은 없다. 관리 포인트를 하나 줄인 대신 지켜야 할 조건이 하나 생긴 셈이다.

## 4. 연동처가 늘면 무엇이 막히나?
- 지금 연동처는 하나다. 그런데 연동은 보통 하나로 끝나지 않는다. 두 번째 연동처가 생기면 각 선택지에서 할 일은 아래와 같다.

| 선택지 | 두 번째 연동처가 생기면 |
|---|---|
| 1. 기존 연동 코드 구조 | 연동처 코드 하나 추가, 상품마다 행 추가. 스키마는 그대로 |
| 2. 마스터 컬럼 | 컬럼 하나를 둘이 나눠 쓸 수 없다. 컬럼을 늘리거나 다른 구조로 옮겨야 함 |
| 3. 전용 테이블 | 연동처 컬럼을 처음부터 두었다면 행 추가, 아니면 2와 같은 문제 |

- 마스터 컬럼은 연동처가 하나일 때 가장 편하다. 대신 **"상품당 외부 ID 하나"를 스키마로 굳힌다.** "확장에 제한이 된다"는 평가가 이 뜻이다.
- 1번은 처음부터 "상품 × 연동처" 모양이라 연동처가 늘어도 데이터만 는다.

**한가지 더!**
- 그런데 1번도 키가 "연동처"다. 연동처가 늘어나는 것 말고 **키의 단위가 바뀌는 경우**가 있다.
	- 연동 계정 하나로 판매 채널 두 곳에 파는 구조였다. 연동처는 하나인데 주문은 판매 채널 단위로 들어온다.
	- 주문에 실린 코드만으로 상품을 특정하려면, 키를 연동처가 아니라 판매 채널 단위로 바꿔야 한다. 이건 새 테이블과 로직이 필요한 일이라 고려할 항목으로 남겨 뒀다.
- "연동처가 늘 때"만 볼 게 아니라 **"무엇 단위로 늘어나는가"**까지 봐야 막히는 지점이 보인다.

## 5. 매핑은 등록 때 미리? 주문이 올 때마다?
- 저장 위치를 정하고 나면 두 번째 질문이 남는다. 주문이 들어오면 외부 ID로 내부 상품을 찾고, 주문 상품 매핑을 거쳐 기존 주문 수집 흐름에 태워야 한다. 이 매핑을 언제 만들까?
	1. **등록 시점에 미리**: 상품을 등록하면서 외부 ID를 받을 때 매핑도 만들어 둔다. 매핑 테이블에는 외부 연동 ID를 넣으려고 만들어 둔 컬럼도 있다.
	2. **주문이 올 때마다**: 미리 만들지 않고, 출고 요청이 들어올 때마다 그 주문 전용 매핑(단건 매핑)을 만든다.

| | 1. 등록 시점에 미리 | 2. 주문이 올 때마다 |
|---|---|---|
| 주문이 왔을 때 할 일 | 만들어 둔 매핑을 찾기만 함 | 매번 매핑을 새로 만듦 |
| 들고 있는 상태 | 상품 수만큼 늘 살아 있는 매핑 | 주문 하나에 한 번 쓰는 매핑 |
| 원본이 바뀌면 | 상품 수정·비활성화, 외부 ID 변경 때 매핑도 같이 고쳐야 함 | 주문 때 원본을 읽으니 따로 맞출 것이 없음 |
| 실패 지점 | 등록 흐름에 매핑 생성까지 들어감 | 주문 흐름에 매핑 생성이 들어감 |
| 남는 것 | 지금의 관계 | 그 주문이 그때 어느 상품으로 이어졌는지 |

- 미리 만드는 쪽은 주문 처리 단계를 줄여 준다. 그런데 매핑이 원본(상품과 외부 ID)의 **사본**이 된다. 원본이 바뀔 때마다 사본도 맞춰야 하고, 둘이 어긋나는 순간 주문이 엉뚱한 상품으로 간다.
- 주문마다 만드는 쪽은 주문이 올 때마다 쓰기 비용을 낸다. 대신 늘 맞춰 둬야 하는 상태가 없다. 그 순간의 원본을 보고 만들고, 만든 뒤에는 그 주문의 기록으로 남는다.
- 처음 결정 항목에는 미리 매핑이 적혀 있었다. 두 방식을 놓고 최종적으로는 주문마다 만드는 쪽으로 정리했다.

> 결과적으로 **매핑은 미리 만들지 않고, 출고 요청이 올 때마다 만들기로 했다.**

## 6. 주문마다 만든다면 키는?
- 기존 매핑은 "주문에 적힌 상품명 → 내부 상품"이다. 상품명이 같으면 같은 매핑을 탄다. 주문마다 매핑을 만들려면 **키가 주문마다 달라야 한다.**
- 그래서 키를 **"채널 상품명 + 채널 주문 번호"**로 만들었다.
	- 이 값을 매핑의 "주문 상품명" 자리에 넣고, 기존 매핑 등록 로직으로 저장한다.
	- 주문 정보 쪽에도 상품명 자리에 채널 상품명, 옵션명 자리에 채널 주문 번호를 넣고, 기존 주문 수집 흐름에 그대로 태운다.
- 좋은 점은 새로 만든 것이 거의 없다는 것이다. 매핑 테이블도, 수집 로직도, 단건 매핑이라는 개념도 이미 있었다. 외부 주문을 기존 흐름이 알아보는 모양으로 바꿔 넣었을 뿐이다.
- 대가도 분명하다.
	- 매핑 테이블에 여러 주문이 같이 쓰는 매핑과 주문 하나짜리 매핑이 섞인다. 행은 주문 수만큼 는다.
	- "옵션명" 자리에 주문 번호가 들어간다. 컬럼 이름과 실제 뜻이 어긋난다.
- 두 번째 대가는 7장의 이야기와 이어진다.

## 7. 기존 컬럼을 빌려 쓰면, 그 자리의 뜻은?
- 외부 주문에는 식별자가 두 개 온다. 장바구니 단위의 **묶음 번호**와 **주문 번호**다.
- 우리 주문에는 주문 번호 컬럼과 보조 주문 ID 컬럼이 있다. 둘을 어디에 넣을지 정해야 했고, 이 자리는 한 번 바뀌었다.

| | 묶음 번호 | 채널 주문 번호 |
|---|---|---|
| 처음 | 보조 주문 ID | 주문 번호 |
| 바꾼 뒤 | 주문 번호 | 보조 주문 ID |

- 자리를 바꾸자 우리 테이블만 바뀐 게 아니었다. 물류 쪽 시스템으로 보내는 **출고·송장 전송 규격도 같이 바뀌었다.** 상품 항목에 보조 주문 ID 두 개가 추가됐다.
- 기존 컬럼을 빌려 쓰는 건 싸다. 그런데 빌린 자리의 뜻은 우리 테이블만의 것이 아니다. 그 값을 받아 가는 하위 전송까지 **같은 뜻을 약속하게 된다.**
	- 3장의 숨김 플래그가 "누가 쓰는지"를 따로 적어 둔 것이라면, 전송 규격은 "무엇을 담는지"를 따로 적어 둔 것이다.

## 8. 결과적으로?
1. 외부 ID를 어디에 둘지는 깔끔함이 아니라 **누가 그 값을 바꿀 수 있나, 연동처가 늘 때 무엇이 막히나**로 골랐다. 기존 범용 구조를 재사용하고, 사용자가 고칠 수 없게 숨기는 플래그로 쓰기 주체를 나눴다. 늘어나는 단위가 연동처인지 판매 채널인지도 같이 봐야 한다.
2. 매핑을 미리 만들면 단계가 줄지만 원본 변경과의 정합성을 떠안는다. 요청 때 만들면 매번 비용을 내는 대신 맞춰 둘 상태를 두지 않는다. 최종적으로는 주문이 올 때마다 만드는 쪽으로 정리했다.
3. 기존 구조를 빌려 쓰면 새로 만들 것이 줄어든다. 다만 빌린 자리의 뜻, 즉 누가 쓰는지와 무엇을 담는지는 플래그나 전송 규격처럼 어딘가에 따로 적어 둬야 한다.
